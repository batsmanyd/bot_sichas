## 1. Архитектура приложения

### 1.1. Состав

Приложение — монолит без шага frontend-сборки:

- backend: один файл `main.py`, Flask + SQLAlchemy;
- frontend: один `index.html` со встроенными CSS и JavaScript;
- хранилище: PostgreSQL через `psycopg` в Railway, SQLite по умолчанию локально;
- production server: Gunicorn `gthread`, 1 worker, 16 threads, timeout `0`;
- realtime: Server-Sent Events (`/api/events`) и резервный polling;
- фоновые задачи: daemon-thread внутри web-процесса для напоминаний о статусе;
- Telegram: Mini App `initData`, необязательный OIDC, webhook, одноразовый handoff-код и исходящие уведомления;
- карта: Leaflet с unpkg, OpenStreetMap tiles, Nominatim reverse geocoding.

`package.json`, npm/yarn/pnpm lock-файл, bundler и отдельная frontend-сборка отсутствуют. Версии frontend-зависимостей не управляются локальным package manager.

### 1.2. Поток данных

1. Браузер получает монолитный `index.html`.
2. Пользователь аутентифицируется через подписанный Telegram `initData`, OIDC или handoff.
3. Flask session хранит `user_id` в подписанной cookie.
4. Запросы непосредственно читают/изменяют SQLAlchemy-модели.
5. После части commit-ов процесс обновляет in-memory `REALTIME_REVISIONS` и будит SSE-клиента.
6. Frontend по SSE-событию не применяет событие локально, а повторно загружает feed/interests/room.
7. Независимо от SSE frontend опрашивает room каждые 10 с, раздел встреч каждые 15 с, остальное каждые 30 с.

### 1.3. Схема данных

Обнаружены таблицы:

- аккаунт и профиль: `user`, `user_profile`, `profile_selfie`;
- присутствие: `presence`;
- встречи: `meeting`, `interest`, `meeting_state`, `meeting_event`, `meeting_feedback`, `meeting_thanks`;
- room: `photo_consent`, `meeting_place`, `meeting_place_location`, `place_vote`, `chat_message`;
- безопасность: `user_report`, `user_block`, `user_moderation`, `action_log`;
- приглашения: `invite_account`, `invitation`;
- уведомления и служебные данные: `user_notification`, `geocode_cache`, `auth_handoff`, `traffic_visit`.

Положительно:

- есть уникальность отклика `(meeting_id, user_id)`, голосования `(place_id, user_id)`, согласия на фото и благодарности;
- приватное selfie шифруется Fernet перед записью;
- точная публичная позиция другого пользователя заменяется стабильной смещённой точкой;
- основные foreign key объявлены.

Недостатки:

- нет Alembic/миграций и таблицы версии схемы;
- схема создаётся через `create_all()` при импорте приложения;
- startup также изменяет существующие данные (очищает телефоны, перешифровывает legacy selfie);
- нет явных `ondelete`, cascade и декларативной политики удаления;
- ограничения максимума участников и одной активной встречи отсутствуют на уровне БД;
- нет индексов/геоиндекса для поиска по координатам;
- нет optimistic version/lock полей для конкурентных изменений.

## 3. Подтверждённые ошибки

### P0-1. Публичная выдача файлов репозитория

`main.py:2738-2743` отдаёт любой существующий файл под `BASE_DIR`. Локально подтверждено:

- `/main.py` → 200;
- `/tests/test_mvp.py` → 200;
- `/.git/config` → 200.

Если приложение стартует без `DATABASE_URL`, оно создаёт `sichas.db` в том же каталоге. Тогда маршрут потенциально отдаёт всю локальную БД, включая аккаунты, координаты, жалобы, чат и зашифрованные selfie. Даже при PostgreSQL раскрытие исходников облегчает поиск атак и показывает служебную структуру.

### P0-2. SSE способен исчерпать весь пул обработки запросов

Procfile запускает 1 worker × 16 gthread. `/api/events` держит request/thread бесконечно. При 16 активных клиентах обычным API-запросам может не остаться свободного потока. `--timeout 0` не освобождает зависшие соединения. Это может проявляться именно как «действия второго пользователя приходят с заметной задержкой», затем как полный timeout.

### P1-1. Не все изменения создают realtime-события

Локально подтверждено: после `POST /api/presence`, `POST /api/meetings` и `DELETE /api/presence` revision пользователя осталась `0`. `POST /api/location` также не вызывает emit по коду.

Следствия:

- новый открытый пользователь/встреча у соседей появится только на следующем polling;
- ручное выключение статуса может оставаться видимым до 30 секунд;
- новая позиция не обновится немедленно;
- жалоба/блокировка не обновляет состояние второй сессии пользователя.

### P1-2. Разрешены две активные подтверждённые встречи

Дополнительный локальный сценарий: пользователь отправил interest в две личные встречи разных владельцев; оба владельца приняли interest с HTTP 200; `/api/interests` вернул две активные подтверждённые встречи. UI показывает только первую в верхней active bar, но backend не гарантирует правило «одна активная встреча».

### P1-3. Жалоба не приходит администратору

`report_user()` сохраняет `UserReport` и опциональный block, но не вызывает `notify_user` для admin, отдельную очередь или внешний moderation alert. Администратор увидит жалобу только при ручном открытии `/api/admin/reports`.

Дополнительно `report_count` вычисляется до `flush/commit` текущей жалобы. При трёх новых жалобах запрос видит только две ранее сохранённые; автоматическое скрытие фактически происходит на четвёртой.

### P1-4. Уведомления «прочитано» фактически не работают

`POST /api/notifications/read` ставит `read_at`, но `GET /api/notifications` не фильтрует `read_at`, всегда возвращает `read: false` и считает все сохранённые элементы непрочитанными. После read напоминание продолжает отображаться непрочитанным, пока статус/встреча остаются активными.

### P1-5. Frontend теряет введённое сообщение при неуспешной отправке

Обработчик кнопки очищает `messageInput` сразу после вызова async `roomAction`, до подтверждения сервера. При offline, timeout или 500 пользователь видит «Не отправлено — повторите», но исходный текст уже утрачен. Аналогично нет локальной очереди/черновика.

### P1-6. «Доставлено ✓» означает только HTTP-ответ отправителю

Статус выставляется после успешного POST и не подтверждает получение/прочтение вторым клиентом. Нет delivery/read receipts. При потере SSE второй пользователь может увидеть сообщение через polling спустя 10–15 секунд.

### P2-1. Неполная модель in-app уведомлений

В БД сохраняются только `presence_reminder` и `meeting_confirmation`. Большинство событий (`interest`, `accepted`, chat, cancel, late, no_show, report) уходят только как best-effort Telegram либо существуют в room. Заявление README об «истории уведомлений» шире реализации.

### P2-2. Внешняя библиотека без SRI и запрещён zoom

Leaflet загружается с unpkg без `integrity`; при недоступности CDN карта не работает. `maximum-scale=1,user-scalable=no` ухудшает доступность для слабовидящих пользователей.

## 4. Ошибки бизнес-логики

### Регистрация и вход через Telegram

Положительно: Mini App `initData` проверяется сервером по HMAC, используется constant-time comparison и проверка `auth_date`. OIDC применяет state, nonce и PKCE.

Риски:

- подписанный `initData` можно повторно использовать в течение 24 часов; `query_id`/hash не отмечается использованным;
- device token действует 180 дней и не имеет server-side revoke/version, logout его не отзывает;
- при отсутствии постоянного `SECRET_KEY` приложение молча генерирует случайный ключ при каждом старте, ломая sessions/device tokens и расшифровку ранее сохранённых selfie;
- вход по 8-значному коду не имеет отдельного rate limit на попытки Telegram-пользователя.

### Статус «Я открыт сейчас» и радиус

- Статус реализован как `active_until = now + 3650 дней`, то есть практически бессрочно до ручного выключения.
- Напоминание через час создаётся daemon-thread, проверяющий раз в минуту. Dedupe защищает от повторов одного периода.
- Фоновый thread не является надёжным scheduler: пропускает выполнение при restart/downtime и дублируется при нескольких web-процессах.
- После подтверждения встречи присутствие обоих участников закрывается.
- Сервер принимает радиус 1–12 км. UI после геолокации стартует с 3 км, но без геолокации silently использует 12 км вокруг фиксированного центра Минска.
- Feed сортируется только по расстоянию, а не по свежести `updated_at` и не по приоритету «только что открылся».

### Создание, закрытие, личные и групповые встречи

- Создание новой собственной встречи отменяет прежние неподтверждённые встречи без realtime/Telegram-уведомления всем ожидающим участникам.
- Проверка одной подтверждённой собственной встречи не учитывает активные встречи, где пользователь является участником.
- В личной встрече два одновременных accept могут пройти проверку до commit и принять двух людей: нет row lock/unique constraint состояния.
- В группе concurrent accept может превысить лимит.
- Любой участник, не только владелец, может выполнить `not_happened` и `reschedule` для всей встречи без согласования.
- Для группового room frontend фактически выбирает только первого `other`: карточка, thank, report и no-show ориентированы на одного человека. Остальные участники не получают полноценного управления.
- Для группы голосование само не подтверждает место; итог может force-confirm владелец. Текст UI при этом описывает двух участников.
- При `leave` interest сначала становится rejected; затем `close_member_presences()` вычисляет уже новый состав и может закрыть присутствие оставшихся, но не ушедшего участника.

### Подтверждение, чат и фотографии

- Чат доступен только подтверждённым участникам — контроль доступа корректный.
- После собственного `complete` чат немедленно скрывается для этого пользователя, даже если второй ещё не подтвердил результат.
- Хранятся только первые 100 сообщений (`order_by(id).limit(100)`), то есть отображаются самые старые 100, а новые после 100-го могут исчезнуть из room.
- Consent на фото можно дать, но нельзя отозвать для конкретной встречи.
- В группе mutual photo раскрывается только если согласились все участники; UI объясняет ожидание «второго», а не всей группы.
- `accepted` visibility раскрывает selfie всем подтверждённым участникам без отдельного meeting consent, что должно быть явно отражено в privacy UX.

### Приглашения и доверие

- Возврат приглашения после первой завершённой встречи защищён сменой статуса `claimed → rewarded`.
- Trust score вычисляется динамически полными сканами, а не материализованно.
- Рейтинги учитываются только для личных встреч; групповые оценки игнорируются без пояснения.
- Оспаривание no-show автоматически обнуляет его влияние без решения администратора; злоупотребляющий пользователь всегда может оспорить отметку.
- Жалобы сами по себе не влияют на trust score; влияют no-show, завершения, thanks и личные ratings.

### Сообщения боту

Путь, отправляющий внутренний room-chat самому Telegram-боту, не обнаружен: chat пишется только в `chat_message`, а Telegram notification адресуется `user.telegram_id`.

Однако webhook отвечает двумя служебными сообщениями на любой входящий текст, который не является валидным кодом. Это может создавать впечатление ошибочной обработки сообщений ботом и лишний spam. Для точного разбора production-инцидента нужны обезличенные webhook/event logs; live-проверка не выполнялась.

## 5. Проблемы синхронизации

### 5.1. Наиболее вероятная причина заметной задержки

Задержка складывается из четырёх механизмов:

1. **Пропущенный emit.** Presence/create/stop/location не будят другого пользователя.
2. **Polling.** В room обновление раз в 10 с, во встречах раз в 15 с, на остальных экранах раз в 30 с.
3. **In-memory event bus.** `REALTIME_REVISIONS/EVENTS` существует только внутри процесса. События теряются на restart и не работают между несколькими worker/репликами.
4. **Thread starvation.** 16 SSE-клиентов способны занять 16 потоков единственного worker; последующие API ждут свободный поток.

Ожидаемая симптоматика:

- чат/place/lifecycle при малой нагрузке — почти мгновенно через SSE;
- появление/исчезновение presence или новой встречи — 10–30 секунд;
- после reconnect/restart — до следующего polling или нового события;
- при 16+ активных SSE-клиентах — непредсказуемые большие задержки и timeout.

### 5.2. Reconnect и потерянные события

- EventSource автоматически reconnect-ится с `retry: 1500`.
- Heartbeat отправляется каждые 15 секунд.
- `Last-Event-ID` и серверный журнал событий отсутствуют.
- После reconnect нет немедленной обязательной полной синхронизации на `onopen`; refresh вызывается только на `onmessage` или polling.
- События схлопываются до последнего на пользователя. Поскольку frontend делает полный reload, это обычно допустимо, но только если событие вообще получено.

### 5.3. Гонки, двойные нажатия и повторы

- Unique constraints частично защищают interest/vote/consent/thanks.
- Rate limit реализован как `COUNT` затем `INSERT`, то есть не атомарен и обходится конкурентными запросами.
- Создание встречи, сообщение, lifecycle event, report и invitation не имеют idempotency key.
- Повтор POST после сетевого timeout может создать дубль meeting/message/event/invitation.
- UI не блокирует большинство action buttons на время запроса, поэтому двойное нажатие реально.
- `maybe_confirm_place` и accept используют read-check-write без lock.

## 6. Безопасность

### Критические риски

- произвольная выдача файлов репозитория и возможной SQLite-БД;
- отсутствие fail-fast при пустом `SECRET_KEY`: случайный runtime key приводит к недоступности selfie после restart;
- source/config disclosure увеличивает поверхность атаки.

### Авторизация и разграничение доступа

Положительно:

- room endpoints проверяют подтверждённое членство;
- решение по interest доступно владельцу;
- admin endpoints сверяют Telegram ID с allowlist;
- report/no-show target проверяется по составу встречи;
- блокировки учитываются в feed/interest.

Недостатки:

- нет CSRF token/origin validation; SameSite=Lax и JSON снижают риск, но не заменяют явную защиту;
- отсутствует общий request body size limit;
- нет отдельного rate limit для auth, profile, presence, invitations и большинства lifecycle endpoints;
- admin authorization завязана только на переменную окружения и текущую session;
- device token невозможно отозвать индивидуально;
- `ProxyFix` без явного ограничения доверенных proxy требует правильной сетевой изоляции Railway.

### HTTP и supply chain

Есть `nosniff`, Referrer-Policy, COOP и `no-store`. Отсутствуют строгий CSP, HSTS, frame-ancestors/X-Frame-Options и Permissions-Policy. Leaflet CDN не имеет SRI. Зависимости заданы диапазонами без lock/hash, поэтому повторная сборка не полностью воспроизводима.

### Персональные данные

- сохраняются Telegram ID, имя, username, возраст, пол, координаты, selfie, жалобы, блокировки и история встреч;
- selfie шифруется на уровне приложения, но ключ производен от session secret и не имеет версии/ротации;
- координаты публично смещаются, однако точные координаты хранятся в БД;
- нет формализованной retention policy для координат, action logs, traffic, reports, auth handoff и geocode cache;
- жалоба удерживает чат как moderation evidence минимум 30 дней, но очистка лениво запускается при последующих запросах, а не гарантированным job;
- нет audit trail действий администратора: report удаляется после решения.

## 7. Работа базы данных

### Транзакции и целостность

- Commit выполняется прямо внутри route/helper, иногда несколько раз за один пользовательский action.
- `notify_user` для persistent notification сам делает commit, разбивая логическую операцию на несколько транзакций.
- Нет retry для serialization/deadlock/transient connection errors.
- Нет глобальной обработки `IntegrityError` и преобразования её в безопасный idempotent response.
- Проверки лимита участников и active meeting выполняются вне lock.
- SQLite не эквивалентен PostgreSQL по concurrency и foreign key behavior; успешные SQLite-тесты не подтверждают production race-safety.

### Миграции

`create_all()` не меняет уже существующие колонки/constraints. Любая эволюция схемы может привести к расхождению окружений. Startup data rewrite повышает риск долгого старта, lock и частично выполненной миграции.

### Запросы

- Feed загружает все активные presence/meeting и фильтрует расстояние в Python.
- Для каждой карточки отдельно читаются profile, selfie и trust.
- `trust_payload()` сканирует все completed states и все feedback для каждого пользователя.
- `/api/interests` читает все встречи всех пользователей и запускает cleanup/дополнительные запросы для каждой.
- Room выполняет множество запросов внутри циклов participants/events/places.
- `ActionLog`, traffic и cache не имеют регулярной очистки.

Это даёт N+1 и близкую к квадратичной деградацию по мере роста данных.

## 8. Производительность

### Backend

- Главный bottleneck — SSE на sync/gthread worker.
- Feed и trust не масштабируются по объёму БД.
- `process_presence_reminders` сканирует все подходящие presence раз в минуту в web-процессе.
- Telegram bot configuration выполняется синхронно из `before_request`; при ошибке повторяется на следующих запросах и может добавить несколько сетевых timeout к пользовательскому запросу.
- Reverse geocode удерживает глобальный process lock и делает `sleep` внутри request thread.
- Нет pagination для feed/interests/chat (chat имеет только неправильный oldest-100 limit).
- Нет cache для trust/profile joins.

### Frontend и мобильный UX

- Весь CSS/JS/HTML находится в одном документе примерно 106 КБ, без code splitting/minification pipeline.
- Каждый realtime event вызывает полные API reload и перерисовку через `innerHTML`.
- Нет AbortController/timeout для `fetch`; запрос может висеть неопределённо долго.
- Silent refresh скрывает ошибки, connection indicator относится только к room.
- Нет service worker/offline режима.
- Текст сообщения очищается до подтверждения.
- Групповой UX фактически рассчитан на одного собеседника.
- Запрещён browser zoom.

## 9. Риски потери данных

1. Пустой/изменённый `SECRET_KEY` делает сохранённые selfie нерасшифровываемыми.
2. Нет backup/restore-процедуры и проверяемых миграций в репозитории.
3. Нет transactional outbox: Telegram notification теряется при временной ошибке после DB commit.
4. Frontend не различает «сервер не получил запрос» и «commit прошёл, ответ потерян».
5. Повтор после timeout может создать дубликат; отказ от повтора может потерять действие.
6. Введённый chat-текст очищается до подтверждения.
7. In-memory realtime события исчезают при restart.
8. Фоновое напоминание пропускается во время downtime.
9. Cleanup выполняется лениво на пользовательских чтениях; данные могут храниться дольше ожидаемого либо удаляться в неожиданном request.
10. Startup rewrite legacy selfie зависит от единственного текущего ключа и не имеет журнала/rollback.

## 11. Безопасный план исправлений

Ниже только предложение; в рамках аудита ничего не исправлялось.

### Этап 0. Изоляция и воспроизводимость

3. Делать startup fail-fast, если production не имеет `SECRET_KEY`, `DATABASE_URL`, корректного `PUBLIC_URL` и нужных Telegram secrets.

5. Определить SLA: p95 отображения действия у второго пользователя ≤2 с, fallback polling ≤5 с для активного room.

### Этап 3. Целостность БД

5. Сделать mutation endpoints идемпотентными по client-generated operation ID.

## 12. Предложение тестового сценария для двух пользователей

Использовать только staging, два тестовых Telegram-аккаунта A/B, отдельного admin C и уникальный `run_id`.

### Подготовка

1. Очистить только данные этого `run_id` через тестовый API/fixture.
2. Открыть A и B на двух реальных мобильных устройствах/WebView.
3. Включить timestamped client logs, server correlation IDs и network throttling.
4. Зафиксировать baseline SSE connection, server revision и число DB rows.

### Основной сценарий

1. A регистрируется через валидный test bot initData; B не должен получить данные A без feed-доступа.
2. A включает «Я открыт сейчас» в 3 км. B должен увидеть A ≤2 с без ручного refresh.
3. Проверить 2,99 км и 3,01 км; точка A у B должна быть смещена, точные координаты не раскрыты.
4. A выключает статус. Карточка у B исчезает ≤2 с.
5. A создаёт личную встречу «сейчас». B видит её ≤2 с.
6. B дважды быстро нажимает interest и одновременно повторяет POST: одна строка interest, один alert владельцу.
7. A дважды принимает interest. Состояние одно, presence обоих закрыто, публичный marker исчез.
8. Оба открывают room. B отправляет сообщение; A получает его ≤2 с. Delivery у B меняется только после server ack; read — только после client ack A.
9. Оба одновременно голосуют за место. Подтверждается ровно одно место.
10. Оба дают photo consent. До второго согласия фото A/B не раскрываются; после — только участникам room.
11. B включает airplane mode, набирает сообщение и нажимает send. Текст остаётся draft. После reconnect пользователь явно повторяет/отменяет; дубля нет.
12. В момент server commit искусственно оборвать ответ. Повтор с тем же operation ID возвращает исходный результат без дубля.
13. Перезапустить realtime worker. После reconnect оба клиента делают snapshot и сходятся к одному revision ≤5 с.
14. A отмечает late/reschedule; B видит ≤2 с. Проверить права: запрещённое изменение получает 403.
15. Завершить встречу обоими, поставить rating, thank; trust меняется один раз.

### Конкурентность и правило одной встречи

1. Создать владельцев A и C и участника B.
2. B откликается на встречи A и C.
3. A и C одновременно принимают B через barrier.
4. Ожидание: ровно одна транзакция успешна, вторая получает 409; у B одна active meeting.
5. Для группы одновременно принять последних двух участников при одном свободном месте; итоговый capacity не превышен.

### Жалобы и admin

1. B жалуется на A один раз; повтор с тем же operation ID не создаёт дубль.
2. Admin C получает staging alert с report ID, но без selfie/точных координат/token.
3. Три независимых reporter создают ровно три жалобы; policy срабатывает на третьей, не четвёртой.
4. A оспаривает no-show; trust не меняется окончательно до admin decision.

### Критерии приёмки

- p95 sync lag ≤2 с, reconnect snapshot ≤5 с;
- 0 дублей при double-click/retry;
- 0 превышений capacity и 0 пользователей с >1 active meeting;
- 0 выдач приватных файлов;
- 0 потерянных drafts при offline;
- 0 секретов/PII в логах;
- все DB constraints и outbox state согласованы после каждого fault injection.

## Итоговая рекомендация

Не расширять нагрузку до устранения P0. В первую очередь закрыть static file disclosure, переработать модель SSE/worker capacity, затем добавить транзакционные гарантии accept/active meeting. После этого исправить missing emits и moderation delivery и только затем оптимизировать UX и производительность.
